# 文档与工程写作规范

## 1. 语言与表达

- 以简体中文为主；标准、协议、API、芯片和软件名称保留官方英文名称。
- 首次出现的缩写给出英文全称和简短中文释义，例如 SIL（Software-in-the-Loop，软件在环）。
- 采用可验证、无歧义的工程表达；避免“高性能”“安全可靠”等无验收定义的形容词。
- 区分“已确认”“已接受”“暂定”“待研究”“待验证”“未完成”。

## 2. 文件与目录命名

- 文件名使用小写 ASCII、数字和连字符；避免空格、中文文件名和含义不明的缩写。
- Markdown 文件使用 `.md`；目录按主题分层，不按作者或日期随意堆放。
- 任务计划采用两位章节号和稳定节点 ID，例如 `01-requirements-architecture.md`、`01-01`。
- 需求 ID 使用 `FR-nnn`、`NFR-nnn`；风险使用 `RSK-nnn`；问题使用 `Q-nnn`；来源使用 `SRC-nnnn`；变更使用 `CHG-nnnn`；ADR 使用 `ADR-nnnn`。
- ID 一经发布不复用；删除或取消的条目保留并注明状态。

## 3. 推荐文档结构

技术专题优先采用：
1. 目的与范围；
2. 术语与缩写；
3. 需求/约束；
4. 方案与原理；
5. 参数、计算和适用条件；
6. 接口与依赖；
7. 风险、安全与失效模式；
8. 验证方法和结果；
9. 未决问题；
10. 来源与变更记录。

不适用的章节可省略，但不得省略关键适用边界和证据。

## 4. 表格与参数

- 参数表必须包含名称、数值/范围、单位、条件、来源/状态。
- 不适用写“N/A”；未知写“待确认”，不得用 0 或空白暗示已知。
- 单位采用 SI；必要时同时给出常用单位并说明换算。
- 范围使用明确上下限；精度、典型值、最大额定值和推荐工作值不得混用。
- 同一事实只维护一个权威位置，其他文档链接或引用其 ID。

## 5. 图表与架构图

- 图必须有编号、标题、图例（如需要）、方向/边界说明和来源。
- 架构图标明组件边界、数据/控制方向、协议和关键接口。
- Mermaid 图用于可维护的文本图；复杂机械/电气图应链接源文件或 CAD/EDA 原生工程，并记录版本。
- 示意图不得冒充比例图、制造图或接线施工图。
- 图中外部素材须记录许可和来源。

## 6. 代码与命令

- 代码块标注语言；命令注明运行目录、操作系统和前置依赖。
- 示例默认使用虚构/安全测试数据；真实硬件命令须明确风险和安全前置条件。
- 配置示例注明默认值、单位、范围、是否必填及版本。
- 不在文档中放置密码、Token、私钥、个人数据或生产凭据。
- 代码片段应尽可能可复制运行；若为伪代码，明确标注。

## 7. 版本与状态

- 每份长期维护的基线文档记录适用项目阶段、状态、最后复核日期和关联 ADR/需求。
- 需求、接口、配置和测试结果通过 Git commit 追溯；影响兼容性的接口修改必须说明版本策略。
- ADR 状态使用“提议中 / 暂定 / 已接受 / 已取代 / 拒绝”。
- 任务状态仅使用“未完成 / 正在进行中 / 已完成”。
- 不覆盖历史决策；以新 ADR 或 CHG 说明替代关系。

## 8. 过期内容复核

以下内容在相关工作启动前及每次重大选型前复核：
- 芯片、板卡和机械部件的数据手册、勘误、生命周期与供货状态；
- 固件、操作系统、构建工具、库和切片器版本；
- 标准、法规、认证路径和适用地域；
- 许可证、安全公告和上游维护状态；
- 价格、采购渠道和替代料信息。

复核时更新访问日期、适用版本、状态和影响项。旧信息保留为历史记录，并标注不再适用的原因。

## 9. 质量检查

- 所有相对链接可解析；文件名大小写与实际路径一致。
- 表格列数一致；代码围栏正确闭合；图表有说明。
- 每个需求、风险、来源和决策 ID 唯一且引用一致。
- 不存在没有来源的关键外部技术参数或合规断言。
- 任务状态与交付物、测试证据一致。
