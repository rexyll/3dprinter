# 贡献与执行指南

## 1. 适用范围

本指南适用于本仓库的需求、设计、来源、代码、仿真、测试和发布文档。全局边界以根目录 [TaskPlan.md](../TaskPlan.md) 的 Guide、Limit 和阶段门禁为准。

## 2. 开始工作前

1. 阅读根目录 `TaskPlan.md`，确认当前阶段、任务指针和禁止事项。
2. 阅读目标章节的 `docs/TaskPlan/<chapter>.md`，确认状态、前置依赖、交付物和验收标准。
3. 检查对应事实源、来源台账、ADR、风险和开放问题，避免重复定义或覆盖未解决冲突。
4. 检查仓库当前内容和 Git diff；不因文件存在就认定任务已完成。
5. 若前置条件不满足，先处理阻塞或登记问题，不得越过依赖强行推进。

## 3. 每个任务节点的必需字段

每个节点必须包含：
- **状态**：仅使用 `未完成`、`正在进行中`、`已完成`。
- **必须完成**：可核对的行动项。
- **禁止事项**：本节点特有边界。
- **前置依赖**：节点 ID 或“无”。
- **交付物**：精确路径、代码、模型或测试报告。
- **验收标准**：可复现、可检查的通过条件。
- **完成证据/当前进展**：完成节点给出提交、测试或审查证据；进行中节点说明已做工作和剩余项。

状态不得仅因文档创建或代码写入而改变。外部阻塞应明确记录原因和解除条件。

## 4. 证据与技术主张

- 关键外部参数、标准条款、器件能力、兼容性和安全主张必须关联来源台账中的 Source ID。
- 用户确认的项目输入必须与外部技术证据分开登记。
- 明确区分事实、设计推导、假设、测试观察和待验证结论。
- 记录产品完整型号、硬件修订、软件/固件版本、标准版本和测试条件。
- 来源不足时写“待核实”，不得补造数字或以二手转载替代原始依据。

## 5. 决策、风险与变更

- 影响系统边界、技术路线、接口、器件选型或安全策略的决定必须创建 ADR。
- 关键未知项进入开放问题表；可能导致伤害、损坏、延误或返工的事项进入风险表。
- 影响已批准基线、需求、接口或验收门槛的变更，先登记 CHG，再分析影响并批准。
- 已取代的 ADR、旧规格和旧测试记录保留历史，不得静默删除。

## 6. 工作块与提交

建议每个工作块聚焦一个可审查目标：
1. 读取相关文件和当前版本。
2. 完成最小范围的文档/代码/测试变更。
3. 检查 Markdown、链接、路径、格式、许可证和安全边界。
4. 检查 diff，确认没有无关覆盖或意外删除。
5. 更新章节 TaskPlan、根 TaskPlan 和 README 导航。
6. 提交到 `main`（按项目授权执行），提交说明使用简洁的 Conventional Commits 风格。
7. 重新从 GitHub 读取提交后的文件，核对实际内容和状态。

提交只证明内容写入版本库，不证明软件构建、仿真或实物验收通过。

## 7. 验证记录

每项验证至少记录：
- 测试 ID、目的和关联需求；
- 软件版本/commit、配置和运行环境；
- 前置条件、步骤和输入数据；
- 预期结果与实际结果；
- 通过/失败/阻塞状态；
- 日志、报告或可复现证据路径；
- 未覆盖范围与已知限制。

SIL、HIL 和实物测试必须明确区分。SIL 通过不得表述为硬件安全或打印质量已验证。

## 8. 第二阶段门禁

在根 TaskPlan 第一阶段完成门禁未通过前，不开展第二阶段的大规模行业资料汇总。可以维护范围目录和治理规范，但不得抢占第一阶段实现资源。
