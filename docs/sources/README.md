# 来源登记与证据规范

> 状态：模板初版，随项目推进持续修订。  
> 适用范围：第一阶段工程决策、技术参数、接口约束、软件依赖、安全分析与测试结论。  
> 维护原则：来源记录必须支持读者从具体结论回溯到原始资料；引用不自动等于结论正确。

## 1. 来源登记字段

每条来源记录至少包含以下字段：

| 字段 | 要求 |
|---|---|
| Source ID | 稳定唯一编号，例如 SRC-0001；不得复用 |
| 标题 | 原始资料的准确标题 |
| 发布机构/作者 | 原厂、标准组织、项目维护者、论文作者或其他发布主体 |
| 来源类型 | 标准原文、官方数据手册、官方应用笔记、官方项目文档、论文、法规原文、社区经验、媒体/营销资料、内部测试、工程推断 |
| 型号/版本 | 明确适用的产品型号、文档版本、固件版本或标准版本；不适用时说明 |
| 发布/修订日期 | 原文可确认的日期；未知则标注未知 |
| URL/定位信息 | 稳定链接；必要时补充章节、页码、表格或代码路径 |
| 访问日期 | 实际访问日期（ISO 8601，YYYY-MM-DD） |
| 支持的结论 | 明确写出该来源支持哪一条具体结论/需求/决策 |
| 证据摘录/定位 | 简短摘录或精确章节/页码/行号，遵守版权限制 |
| 适用范围 | 地区、产品修订、工作条件、材料、环境或其他边界 |
| 可信度与限制 | 说明来源权威性、独立性、时效性及缺陷 |
| 关联项 | 需求 ID、ADR、风险 ID、测试 ID 或文件路径 |
| 复核状态 | 待复核、已复核、过期、存在冲突 |

## 2. 证据类型与使用规则

- **标准原文/法规原文**：用于标准条款、法规义务和符合性范围；必须记录准确版本、发布日期及适用地域。不得仅凭摘要宣称合规。
- **官方数据手册/规格书**：用于具体器件型号的电气、时序、热和机械参数；必须核对完整料号、修订版和测试条件。
- **官方项目文档/源代码**：用于软件功能、接口、版本和实现行为；需锁定发布版本或 commit，不把主分支当前行为泛化到旧版本。
- **论文/学术资料**：用于研究结论和方法；记录实验条件、样本范围和可复现性限制。
- **社区经验/论坛讨论**：用于发现问题和实践线索，不单独作为安全关键参数或合规结论的最终依据。
- **媒体/营销资料**：可用于产品存在、厂商公开主张或市场线索；性能主张需独立验证。
- **内部测试**：必须记录环境、硬件/软件版本、步骤、原始数据、结果和偏差；只支持该测试范围内的结论。
- **工程推断**：明确标记为推断，写出前提、计算过程和不确定性；不得伪装成来源事实。

## 3. 冲突与过期处理

1. 先确认资料是否针对同一型号、硬件修订、软件版本、标准版本和工况。
2. 官方原始资料优先于转载；现行版本不自动适用于旧设备或旧标准。
3. 不同来源存在冲突时并列记录，不得挑选有利数据而隐去冲突。
4. 对影响安全、选型或接口的冲突，建立问题/风险记录并暂停相关冻结决策。
5. 定期复核易变信息：芯片生命周期、固件版本、软件依赖、供应状态、法规和标准版本。
6. URL 失效时记录失效日期，并尽可能寻找发布机构的归档副本；不得静默替换为不明转载。

## 4. 引用与结论写作规范

- 技术参数应尽量引用原厂规格书/标准原文，并同时注明型号、版本和条件。
- 每个关键结论应紧邻引用，或通过 Source ID 明确关联来源台账。
- 区分“来源明确陈述”“本项目推导”“待验证假设”和“测试观察”。
- 不能由来源支持的精确数字不得写入设计基线。
- 引用只证明信息出处，不代表该信息已在本项目环境中验证。
- 不将不同厂商、不同修订或不同测试条件的数据直接横向比较，除非说明归一化方法。
