# 请求账本持久化与崩溃恢复契约

- **状态**：架构设计提案；待 01-03 审查，未实现、未验证
- **版本**：0.1
- **日期**：2026-11-04
- **关联任务**：01-03
- **依据**：[请求/事件/会话一致性语义](request-event-session-semantics.md)、[请求账本与事件同步责任矩阵](request-ledger-responsibility-matrix.md)、[载荷规范化规则](request-payload-canonicalization.md)、[接口控制文档](interface-control.md)
- **边界声明**：本文定义持久化记录语义、崩溃窗口和恢复裁决，不选择最终数据库/NVM 产品，不冻结线协议，不证明 MCU/NVM 掉电特性、物理动作安全或 exactly-once。

## 1. 设计目标

1. 设备侧 TASK 是副作用请求是否获准、执行阶段和设备已知结果的权威裁决方；HOST 账本只保存主机观察到的事实。
2. 对每个可能产生物理副作用的请求，持久化身份、载荷指纹、执行阶段和结果证据，且可检测记录损坏/截断。
3. 在无法证明动作是否发生时返回 `Unknown`，不因记录缺失、超时或重启而把请求解释为“未执行”。
4. 同一原始请求身份（`device_id + session_id + request_id`）及相同载荷只能对应一个逻辑执行；相同身份不同载荷必须冲突拒绝。
5. 事件发布与结果记录通过可恢复的 outbox 语义关联，避免“设备结果已持久化但事件丢失”导致主机永远无法同步。
6. 不承诺跨物理动作的数据库事务。运动、挤出、加热等不可逆/非幂等动作的恢复必须结合可信观测与安全策略。

## 2. 请求账本记录模型

### 2.1 最小逻辑记录

| 字段 | 含义 | 约束 |
|---|---|---|
| device_id | 设备身份 | 与设备配置/身份体系一致 |
| session_id | 请求所属原始会话 | 不因重连改写 |
| request_id | 会话内请求唯一标识 | 同身份重试沿用；新业务意图使用新 ID |
| task_id | 关联作业 | 无作业关联时明确为空 |
| correlation_id | 异步结果关联 | 不作为幂等身份替代品 |
| payload_fingerprint | 规范化业务载荷摘要 | 必须同时记录算法/profile/schema 标识 |
| canonicalization_profile | 规范化规则 ID/版本 | 不得静默替换 |
| payload_schema_id/version | 业务载荷 schema | 决定载荷解释 |
| operation / effect_class | 操作名及副作用分类 | 至少区分只读、可重复设置、非幂等物理动作、任务控制 |
| phase | 最近持久化阶段 | 使用 3 节阶段模型 |
| boot_epoch | 设备启动代际 | 每次启动必须可区分；持久代际不可用时声明无法跨启动确认 |
| record_revision | 单条记录修订序号 | 单调递增，防止旧写覆盖新写 |
| event_stream_id / event_sequence | 结果事件流身份与水位 | 与 outbox 记录一致 |
| result / diagnostic | 结果与诊断 | 终态必须保存可审计结果 |
| effect_evidence | 副作用边界与观测证据 | 区分“已请求”“已调用”“已观测” |
| integrity metadata | 格式版本、长度、校验/提交标记 | 用于检测撕裂写入和损坏 |

记录还应包含接收时间、更新时间、固件构建标识和兼容 profile；时间戳仅用于诊断，不用来裁决因果顺序。

### 2.2 身份与载荷冲突

- 主键语义：`device_id + session_id + request_id`。
- 已存在相同主键且 fingerprint、profile、schema、operation 一致：返回已有阶段/结果，不创建第二次执行。
- 已存在相同主键但任一载荷身份字段不同：返回稳定冲突错误，保留原记录，不覆盖、不执行。
- fingerprint 必须基于业务载荷规范化结果；message_id、重试计数、传输时间等传输元数据不得进入摘要。
- 摘要只能证明载荷字节/语义身份一致，不能证明调用方身份、授权有效或物理动作已执行。

## 3. 持久化阶段与执行门

建议的逻辑阶段（不是冻结的线上枚举）：

`Received → Accepted → DispatchIntentDurable → EffectObserved → OutcomeDurable → EventOutboxDurable → Published`

终止/异常分支包括 `Rejected`、`Failed`、`Unknown`。实现可合并内部阶段，但不得丢失下列语义边界：

1. **Received**：已验证消息身份和基本格式；尚未承诺执行。
2. **Accepted**：TASK 已通过业务状态守卫并持久化接纳事实；尚未允许调用物理副作用。
3. **DispatchIntentDurable**：在调用任何可能产生副作用的执行器之前，已将“即将尝试调用”的意图可靠提交。该记录不是动作已发生的证明。
4. **EffectObserved**：执行器/传感器/位置反馈提供了动作开始或进展的证据；证据来源与置信边界必须记录。仅有函数调用返回不必然等于物理动作已发生。
5. **OutcomeDurable**：结果及已知部分副作用已可靠提交。成功/失败均需定义完成条件。
6. **EventOutboxDurable**：与结果关联的事件身份、stream sequence 和事件内容已与结果原子提交，或通过等效恢复机制保证不会产生无记录事件。
7. **Published**：事件已交给传输层；该状态不表示 HOST 已收到。未获主机确认时可按同一 event_id/sequence 重发。

**关键执行门**：只有在 `DispatchIntentDurable` 提交成功后，TASK 才能调用非幂等副作用执行器。若持久化失败，必须拒绝/保持未执行，不得“先动作后补记账”。若在提交意图后、调用前崩溃，恢复端无法仅凭该记录证明调用未发生，保守结果仍为 Unknown；若实现能证明调用门尚未越过（例如独立、可信的执行器事务标记），才可细化裁决。

## 4. 崩溃/掉电窗口裁决矩阵

| 崩溃窗口 | 重启后可证明的事实 | 恢复裁决 | 是否自动重放 |
|---|---|---|---|
| A. Received 已持久化，Accepted 尚未提交 | 请求已识别；未进入接受阶段 | 可报告 Received/待重新裁决；重新校验当前状态与安全守卫 | 不自动执行 |
| B. Accepted 已持久化，DispatchIntent 尚未提交 | 已接纳，但按执行门不允许调用副作用 | 可恢复为待派发候选；必须重新检查设备状态、安全锁存和任务上下文 | 默认不自动；经明确恢复策略重新授权后才可派发 |
| C. DispatchIntent 已提交，执行器调用前或调用中掉电 | 仅能证明曾准备尝试调用；无法证明调用是否发生/完成 | Unknown；进入同步受限状态，查询独立观测或要求人工处置 | **禁止** |
| D. 动作已开始，Outcome 尚未提交 | 有开始证据但结果不完整，物理状态可能已改变 | Unknown/部分执行；先执行安全恢复和状态重建 | **禁止** |
| E. 动作已完成，Outcome 尚未提交 | 若无独立可持久化完成证据，无法证明完成；若有可信证据则按证据恢复 | 默认 Unknown；仅凭传感器/位置等独立证据满足完成判据时可重建结果，且记录重建来源 | **禁止** |
| F. Outcome 已提交，Outbox 尚未提交 | 结果已持久化，但事件可能不存在 | 通过结果记录恢复事件，或将结果查询作为权威同步路径；不得重新执行动作 | 不重放动作 |
| G. Outbox 已提交，事件尚未发送 | 结果和事件待发布 | 从 outbox 发送原 event_id/sequence | 只重发事件，不重放动作 |
| H. 事件已发送，HOST 未收到/未确认 | 设备端结果和事件仍在账本/outbox | 允许重发完全相同事件身份和内容；接收端去重 | 只重发事件 |
| I. Outcome 已提交，事件已确认但 HOST 账本丢失 | 设备端仍保有权威结果（若记录完整） | 新会话查询原 session_id + request_id，重建主机审计视图 | 不重放动作 |
| J. 设备账本损坏、格式不兼容或代际无法确认 | 不能可靠解释历史请求 | 标记 RESULT_UNKNOWN / LEDGER_UNAVAILABLE，禁止危险控制放行，要求恢复/人工处置 | **禁止** |

上述默认规则针对非幂等或物理副作用请求。只读查询可以重新查询；可重复设置类操作也必须先证明其语义确为“设定目标状态”而非增量动作，并重新通过安全守卫，不能仅按操作名称分类。

## 5. 启动代际、事件水位与记录完整性

- 每次设备启动产生新的 `boot_epoch`。首选可验证的单调持久代际；若硬件无法保证其原子更新/寿命/恢复，则使用随机启动 nonce 作为会话隔离补充，但不能把随机 nonce 当作持久账本完整性的证明。
- `session_id` 与 boot_epoch 关联，避免设备重启后旧会话被误认为当前会话。
- event stream sequence 的分配与 outbox 提交必须具备一致性规则：不得发布没有可恢复记录的序号；不得因重启复用已发布序号。
- 快照必须携带每个事件流的 watermark，且快照状态与 watermark 必须来自同一一致性切面，或具备等价的版本重试机制。
- 记录需能检测截断、撕裂写入、重复提交和格式版本不兼容。发现损坏时不得跳过损坏记录后把后续记录解释为连续可信历史。
- 账本回收策略必须覆盖请求重试、迟到响应、重连查询和审计保留窗口；在这些窗口和持久化容量尚未确定前，不定义具体保留天数/条数。
- 固件升级、恢复出厂设置、配置迁移和存储格式升级必须定义 ledger 保留/迁移/显式失效行为。不得静默清空未决副作用记录。

## 6. 存储原型候选（不冻结）

| 候选 | 适用验证目标 | 优点 | 主要风险/限制 |
|---|---|---|---|
| SQLite 事务原型（Host/SIL） | 状态转换、唯一约束、事务、outbox 原子提交、崩溃恢复逻辑 | 查询方便、事务语义成熟、便于注入进程崩溃 | 不代表 MCU NVM；文件系统/设备掉电语义仍需单独验证 |
| Append-only journal（Host/SIL） | 顺序日志、提交标记、校验和、截断恢复 | 易观察写入顺序与 torn-tail 行为 | 索引、压缩、并发和回收需自行设计 |
| MCU NVM/Flash 适配器仿真 | 记录大小、擦写粒度、掉电中断、磨损策略接口 | 可将硬件约束显式建模 | 只能验证模型假设，不能证明真实芯片行为 |
| 真实 MCU NVM 实现 | 后续 HIL/硬件验证 | 可测试真实写入与复位行为 | 依赖最终 MCU/存储器/电源设计；当前未选型 |

**建议顺序**：先用 Host 侧 SQLite 或 append-only journal 实现可测试的账本状态机和故障注入接口；两者通过 ADR 比较后再选。随后定义抽象持久化接口及 MCU NVM 适配器，不把 SQLite 直接带入实时固件，也不把 Host 原型结果宣称为硬件掉电证明。

## 7. 最小故障注入测试矩阵

| 测试 ID | 注入点 | 预期断言 |
|---|---|---|
| LEDGER-CRASH-001 | Received 提交后崩溃 | 重启可查询 Received；无副作用 |
| LEDGER-CRASH-002 | Accepted 提交后、DispatchIntent 前崩溃 | 不伪称已执行；恢复前重新校验安全守卫 |
| LEDGER-CRASH-003 | DispatchIntent 提交后、执行器调用前崩溃 | Unknown；不自动调用执行器 |
| LEDGER-CRASH-004 | 执行器调用/动作开始后崩溃 | Unknown/部分执行；不重复调用 |
| LEDGER-CRASH-005 | 动作完成后、Outcome 提交前崩溃 | 无独立可信完成证据时 Unknown；不重放 |
| LEDGER-CRASH-006 | Outcome 提交后、Outbox 提交前崩溃 | 恢复结果，不重新执行；事件可重建或通过查询同步 |
| LEDGER-CRASH-007 | Outbox 提交后、事件发送前崩溃 | 重发同 event_id/sequence，动作执行次数仍为 1 |
| LEDGER-CRASH-008 | 事件发送后、HOST 确认前崩溃/断连 | 允许事件重发；HOST 只应用一次 |
| LEDGER-CRASH-009 | 相同身份不同 fingerprint | 冲突拒绝，原记录不变，副作用次数不增加 |
| LEDGER-CRASH-010 | 日志尾部截断/校验失败 | 检测损坏，未决请求 Unknown，不静默当作空账本 |
| LEDGER-CRASH-011 | boot_epoch 更新中断/回绕模拟 | 不复用旧会话；无法证明代际时限制同步 |
| LEDGER-CRASH-012 | 快照 watermark 与 outbox 序号竞态 | 不漏事件、不重复应用；无法形成一致切面则同步失败 |

所有测试必须记录：注入点、持久化介质模型/版本、固件/Host 构建、请求身份与 fingerprint、重启代际、执行器调用次数、可观测副作用、恢复裁决、事件 ID/sequence 和最终诊断。测试不得把“进程重启成功”当作“物理动作安全恢复”。
