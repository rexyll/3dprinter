# 请求、事件与会话一致性语义

- **状态**：逻辑协议语义提案；待 01-03 设计审查，具体编码/传输和时间预算未冻结
- **版本**：0.1
- **日期**：2026-11-04
- **关联任务**：01-03
- **依据**：[接口控制文档 ICD](interface-control.md)、[任务状态转换契约](task-state-transition-contract.md)、[任务状态机 SIL 测试规格](../verification/task-state-test-spec.md)
- **需求关联**：SYS-002、SYS-009、SYS-013、SYS-014；SIL-002、SIL-008、SIL-009、SIL-010
- **边界声明**：本文定义模块间必须保持的逻辑一致性，不定义线上字节格式、传输协议、序号位宽、缓存容量或数值超时；不证明真实设备安全。

## 1. 设计目标与不变量

1. 请求是否发送、对端是否接收、是否接受、是否执行及是否完成必须是不同事实。
2. 任何请求结果不确定时必须保留 Unknown；不得把超时、本地发送成功或连接恢复解释为设备未执行/已执行。
3. 同一请求的重试不得造成重复运动、挤出、加热或任务控制副作用。
4. 新会话只能以新会话的权威同步结果建立当前状态；旧会话事件不得覆盖新会话。
5. 事件顺序必须在明确作用域内可判断；出现无法安全裁决的缺口时，状态机不得越过缺失事件推进到更成功状态。
6. 设备侧 TASK 是任务状态的最终裁决者；HOST/COMM 负责请求关联、去重、未知结果管理和同步。

## 2. 标识与作用域

| 标识 | 逻辑作用域 | 约束 |
|---|---|---|
| device_id | 设备身份 | 在主机配置/设备发现域内稳定；不得用 session_id 替代 |
| session_id | 一次成功建立的通信会话代际 | 每次重新建立会话生成新值；旧会话不得复用为新会话 |
| request_id | 单一请求 | 在 session_id 内唯一；请求重试沿用原 request_id；新业务意图必须使用新 request_id |
| message_id | 单条消息 | 在发送方声明的命名空间内唯一；用于消息级去重/关联 |
| task_id | 一次作业生命周期 | 新作业使用新 task_id；不得因重连改变任务身份 |
| event_id | 单条事件 | 在声明的事件流/会话域内唯一；重复事件可识别 |
| sequence | 一个明确事件流 | 同一流内单调递增；作用域和重置边界必须随流标识可识别 |
| correlation_id | 请求与异步结果关联 | 一个业务请求的接受、进度、完成/失败结果可关联到原请求 |

所有响应/事件必须携带适用的 device_id、session_id、request_id、task_id、event_id、sequence 和 correlation_id；不适用的字段可以明确为空，但不得省略其作用域约定。时间戳仅供诊断和时延分析，不取代序号或因果关联。

## 3. 请求生命周期与结果裁决

### 3.1 逻辑阶段

`Created → Sent → Received → Accepted → InProgress → Completed`

允许的非成功分支：
- 任一对端校验阶段可产生 `Rejected`，并给出稳定错误类别。
- 对端明确报告执行失败时为 `Failed`，必须附已知部分执行状态。
- 调用方失去确定性时为 `Unknown`。Unknown 是调用方对证据不足的判断，不是设备任务状态，也不意味着对端失败或停止。

`Received` 仅表示对端识别消息；`Accepted` 表示对端同意接纳请求；`InProgress` 表示已开始执行；`Completed` 表示请求定义范围内动作完成。不得跨级推断。

### 3.2 结果存储和状态查询

- HOST/COMM 为每个请求维护 request ledger：原始请求摘要、session_id、request_id、task_id、发送事实、最近确认阶段、最终结果或 Unknown。
- TASK 侧应能按原始 `session_id + request_id` 查询已知请求状态；返回值至少区分未识别、已接受/执行中、已完成、已拒绝/失败和无法确定。查询必须明确指向原会话的请求身份，不得把新会话中的同名 request_id 当成同一请求。
- 断连后，HOST 对所有无终态证据的请求标记 Unknown（并保留最后已确认阶段）；不得将其改写为 Rejected。
- 重连后先查询设备当前 task 状态及未决 request_id 的结果。若设备无法证明请求结果，保留 Unknown 并要求上层按安全策略处理；不得自动重新提交原动作。
- 请求结果查询是只读操作，不得触发原请求的动作副作用。

### 3.3 请求重试分类

| 操作类别 | 默认规则 | 允许重试条件 |
|---|---|---|
| 只读查询（能力、状态、遥测） | 可重新发起查询 | 使用新 request_id 或明确的查询关联规则；响应必须带当前 session_id/新鲜度信息 |
| 有副作用的任务控制（Start/Pause/Resume/Cancel/ClearFault） | 不盲目重发 | 先查询原 request_id/任务状态；若原请求结果可确认，再按业务状态决定是否发起新的意图 |
| 运动/挤出/加热设定或动作命令 | 不盲目重发 | 只有接口声明幂等键、作用域、参数冲突规则及设备端去重保持期后，才可使用同一幂等身份重试 |
| 会话建立/握手 | 可重新建立新会话 | 每次新建会话生成新 session_id；不得沿用旧会话状态作为同步完成证据 |

当前逻辑基线不声明任何运动/挤出/加热动作天然幂等。未来若声明幂等，必须说明幂等键由哪些字段构成、有效作用域、保留期、冲突响应、重启后的持久性和过期后的行为。

### 3.3 设备侧持久化与崩溃恢复约束

- 对副作用请求，设备侧 TASK 必须在调用执行器前可靠提交 DispatchIntent；持久化失败时不得调用执行器。
- DispatchIntent 只表示“准备尝试调用”，不证明物理动作已开始或完成。崩溃发生在该记录提交之后、结果持久化之前时，默认裁决为 Unknown，禁止自动重放。
- Accepted 已提交但 DispatchIntent 尚未提交时，按执行门规则可证明动作调用尚未获准；恢复后仍须重新检查任务状态、安全锁存和执行上下文，不得无条件自动启动。
- Outcome 已持久化但事件未发送时，只恢复或重发同一 event_id/sequence；不得重新执行原动作。
- 设备侧账本记录、启动代际、outbox 和 A～J 崩溃窗口的详细字段与恢复矩阵见[请求账本持久化与崩溃恢复契约](request-ledger-persistence-and-recovery.md)。该契约是设计提案，不是持久化实现或硬件掉电验证。

## 4. 重复请求处理

对同一 `session_id + request_id`：

1. **同 ID、同请求摘要、处理中**：返回当前已知阶段/原关联，不再次执行副作用。
2. **同 ID、同请求摘要、已有终态**：返回原终态结果，不再次执行。
3. **同 ID、不同请求摘要**：拒绝为请求标识冲突（建议映射 PROTOCOL_ERROR 或 INVALID_ARGUMENT）；不得覆盖原请求，也不得执行新载荷。
4. **新 request_id**：视为新的业务意图，必须重新执行状态守卫和权限/能力校验。
5. **旧 session 的重复请求**：拒绝作为当前会话操作；只能返回可查询的历史记录，不能改变当前设备状态。

TASK/设备端的去重记录必须至少覆盖请求可能产生副作用的生命周期。若设备重启后去重记录不持久，重启前未决请求必须在恢复后标记为 Unknown，不能假设安全重放。去重记录的存储方式/保留时长留待 01-04 平台选型与 05 固件设计。

## 5. 事件排序、重复与缺口

### 5.1 事件流模型

- 每个事件流有明确 stream identity，至少能区分 device/session 和事件类别或任务作用域。
- 同一流的 sequence 单调递增；具体起点、位宽、回绕和持久化策略待协议实现选择。
- event_id 用于识别同一事件的重复投递；sequence 用于识别流内位置和缺口。两者不可互相替代。
- 相同 event_id 且载荷摘要相同：重复投递，记录重复计数/诊断但不得重复应用状态转换或副作用。
- 相同 event_id 但载荷不同，或同一流相同 sequence 对应不同 event_id：协议冲突，拒绝冲突事件并进入重新同步/故障诊断路径。
- sequence 小于等于已应用水位且非可识别的完全相同重复事件：视为过期/冲突事件，不得回滚状态。
- sequence 出现缺口：记录 gap；不得应用依赖缺失事件才能成立的终态/成功状态。接收方应请求重放缺失区间或获取权威状态快照。
- 乱序事件可暂存等待缺口填补；缓存容量和等待时长由具体协议/平台定义。缓存耗尽或无法补齐时，放弃增量裁决并重新同步，不得静默跳过缺口。
- 不同事件流之间没有天然全序；跨流依赖必须用 correlation_id、因果引用或权威快照明确表达，不得按墙钟时间强行排序。

### 5.2 事件应用规则

1. 先验证 session_id、stream identity、event_id、sequence 和关联任务身份。
2. 再执行重复/冲突/过期/缺口判定。
3. 只有顺序可信且满足状态转换守卫的事件，才能交给 TASK 状态机应用。
4. 事件被拒绝、丢弃、缓冲或触发重同步时，必须记录原因和原始标识。
5. 任何旧会话事件、旧 task_id 事件不得更新当前任务；事件可归档至其原上下文。

## 6. 重连与同步握手

### 6.1 连接阶段

`Disconnected/ConnectionLost → Connecting → Synchronizing → Connected`

在 Synchronizing 完成之前，禁止提交可能产生运动、挤出、加热或任务状态副作用的控制请求。只读握手/状态查询除外。

### 6.2 同步交换的逻辑内容

新会话建立后，HOST 至少需要取得：
- 当前 device identity、固件/协议能力版本和新 session_id；
- 当前设备侧 task_id、Job State、任务执行位置/进度的可信度；
- 当前 fault latch、活动故障标识及是否允许复位的状态（不要求在握手时复位）；
- 当前事件流标识及每条流的已确认 sequence watermark；
- 可查询的旧请求结果或对其无法确定的明确答复；
- 当前遥测及其来源/新鲜度标记。

### 6.3 快照与增量事件竞态

同步快照必须带有每条事件流的水位（watermark）。快照之后到达的增量事件只有在 sequence 严格晚于对应水位且会话身份匹配时才可应用。若快照与增量无法建立一致切面，则保持 Synchronizing，重新读取快照或重放缺失事件；不得先显示 Connected 再异步“修正”状态。

### 6.4 未决请求恢复裁决

| 重连查询结果 | HOST/COMM 处理 | 是否重放原动作 |
|---|---|---|
| 明确未被设备识别，且设备端能证明该 request_id 未接受 | 保留原请求审计记录；是否发起新业务请求由上层重新决策 | 不自动重放；上层可显式创建新 request_id |
| 已 Accepted/InProgress | 关联原 task/request，继续订阅/查询状态 | 否 |
| 已 Completed | 记录原请求完成结果，校验 task_id/session lineage | 否 |
| 已 Rejected/Failed | 记录原结果和错误 | 否 |
| 设备无法查询、设备重启丢失记录或结果矛盾 | 保留 Unknown；连接可否进入 Connected 取决于当前任务/故障状态能否安全同步 | 否 |

### 6.5 Connected 的准入条件

只有同时满足以下条件才允许 Synchronizing → Connected：
- 设备身份与会话代际明确；
- 能力、任务状态和故障锁存状态均已取得且通过一致性校验；
- 事件流水位已建立，不存在未处理且影响当前状态的序号缺口；
- 旧会话未决请求已逐项得到确定结果；若仍有可能产生副作用的请求处于 Unknown，则必须保持 Synchronizing/受限态，直至经明确的安全处置/人工裁决完成，不能仅因上层隐藏控制按钮就视为同步完成；
- 主机已将旧遥测标记为 stale，并仅发布新会话下重新取得的遥测为当前值。

如未满足，保持 Synchronizing 或回到 Disconnected；不得伪造同步成功。

## 7. 错误类别建议映射

| 条件 | 建议错误/诊断类别 | 处理 |
|---|---|---|
| 同 request_id 不同载荷 | PROTOCOL_ERROR | 拒绝新载荷，保留原请求记录 |
| 相同 event_id 不同载荷 | PROTOCOL_ERROR | 拒绝冲突事件并重新同步 |
| sequence 缺口 | EVENT_GAP | 暂缓依赖事件，补齐或获取快照 |
| 旧 session 事件/请求 | STALE_SESSION | 隔离归档，不应用到当前状态 |
| 旧 task_id 事件 | STALE_TASK | 归档到原任务，不改变当前任务 |
| 请求结果不可查询 | RESULT_UNKNOWN | 保留 Unknown，不重放非幂等动作 |
| 同步快照与增量矛盾 | SYNC_INCONSISTENT | 保持 Synchronizing，重新同步 |

以上为逻辑诊断类别建议；是否成为 ICD 稳定错误码，须在 01-04 统一错误 schema 时决定。

## 8. 对现有 SIL/STM 测试的新增要求

在现有 STM-NEG-001～015 基础上补充：
- 同 request_id 同载荷重复提交：不重复执行，返回同一请求阶段/结果。
- 同 request_id 不同载荷：明确拒绝且不覆盖原请求。
- event_id 重复及载荷冲突：分别去重与协议错误。
- sequence 缺口、乱序补齐、缓存无法补齐：不越过缺失事件推进终态；必要时重同步。
- 重连快照水位与快照后事件：只应用水位之后且 session 匹配的事件。
- 旧请求查询返回 Accepted/InProgress/Completed/Unknown：分别验证不重放与正确关联。
- 设备重启后丢失去重账本：未决动作仍为 Unknown，不盲目重放。

详细可执行用例应追加到 [任务状态机 SIL 测试规格](../verification/task-state-test-spec.md)。

## 10. 审查结论

本文形成请求生命周期、请求去重、事件顺序、会话隔离和重连同步的逻辑语义提案，可作为 ICD、状态机和 SIL 测试设计的统一输入。仍需审查其与具体协议能力、固件重启/持久化行为、错误 schema 和安全状态策略的可实现性。本文不是已冻结协议，也不表示代码已实现或测试已通过。
