# 请求载荷规范化、摘要与幂等身份规则

- **状态**：逻辑设计提案；摘要算法、线上编码及兼容窗口未冻结
- **版本**：0.1
- **日期**：2026-11-04
- **关联任务**：01-03
- **依据**：[请求/事件/会话一致性语义](request-event-session-semantics.md)、[请求账本与事件同步责任矩阵](request-ledger-responsibility-matrix.md)、[接口控制文档 ICD](interface-control.md)
- **需求关联**：SYS-002、SYS-009、SYS-013、SYS-014；SIL-002、SIL-008、SIL-009、SIL-010
- **边界声明**：本文定义逻辑身份与载荷比较规则，不冻结具体 JSON/CBOR/Protobuf 等序列化格式，不证明密码学实现安全、持久化原子性或真实设备安全。

## 1. 目的与关键区分

请求去重必须区分三个不同概念：

1. **请求身份（Request Identity）**：回答“这是哪一次业务请求”。逻辑主键为 `device_id + session_id + request_id`；设备端必须在设备身份域内隔离会话代际。
2. **幂等键（Idempotency Key）**：供请求发起方在同一业务意图的重试中复用。当前逻辑上由原始 `session_id + request_id` 承担，不是另一个可随重试变化的随机值。
3. **载荷指纹（Payload Fingerprint）**：回答“同一请求身份携带的操作内容是否相同”。由规范化配置标识和规范化载荷字节计算摘要得到。

`request_id` 相同但载荷指纹不同，必须视为协议冲突；`request_id` 不同，即使载荷相同，也不能自动合并为同一动作。摘要相同也不能替代 TASK 的状态守卫、权限检查或安全检查。

## 2. 规范化输入模型

在计算摘要前，接收方必须先完成 schema 版本识别和严格结构校验。参与指纹的逻辑封装至少包含：

| 字段 | 作用 | 规则 |
|---|---|---|
| `interface_version` | 接口语义版本 | 必须明确；不能只依赖传输连接协商的隐含版本 |
| `operation` | 操作类型 | 使用稳定、大小写敏感的枚举标识 |
| `payload_schema_id` | 载荷 schema 身份 | 标识字段集合、类型、单位和语义 |
| `payload_schema_version` | schema 版本 | 不同版本不得默认视为相同 |
| `canonicalization_profile` | 规范化配置版本 | 明确字段排序、数值和字符串规则 |
| `payload` | 操作参数 | 仅包含 schema 明确允许的字段 |

设备身份、session_id、request_id、task_id 和 correlation_id 用于请求关联和账本主键；其中 correlation_id、传输 message_id、重试次数、发送时间、接收时间等诊断/传输元数据**不进入载荷摘要**。device_id/session_id/request_id 仍必须与摘要一同存储，不能因为未参与摘要就忽略其身份约束。

## 3. 规范化处理顺序

推荐采用以下确定性处理流水线：

1. **版本解析**：识别 interface_version、payload_schema_id/version、canonicalization_profile；不支持的版本明确拒绝或进入兼容适配层，禁止猜测。
2. **严格解析**：拒绝重复对象键、非法编码、截断输入、未知必需结构、类型不匹配及 schema 不允许的字段。不得采用“最后一个重复键覆盖前一个”的解析行为。
3. **语义校验**：校验单位、坐标/模式、枚举、范围、权限和当前操作类别。规范化不能把非法值修正成合法值。
4. **确定性字段编码**：按 schema 定义的稳定字段顺序编码；映射/对象键按明确规则排序；数组保持顺序，除非 schema 明确声明其为无序集合并定义排序键。
5. **数值处理**：
   - 整数按 schema 声明的有符号/无符号宽度和字节序进行逻辑编码；溢出拒绝。
   - 物理量必须先按 schema 的明确单位与精度语义处理。若协议使用定点整数，比例因子由 schema 版本定义；若使用十进制文本，必须规定唯一格式。
   - 禁止依赖不同语言运行时的默认浮点字符串化；拒绝 NaN、正负无穷及未定义的负零语义。
   - 不得把不同单位或不同坐标模式下数值相同的字段当成语义相同。
6. **字符串处理**：采用 UTF-8 的确定性编码。默认保留 schema 允许字符串的原始 Unicode 码点序列，不自动做 NFC/NFD、大小写折叠或去空格；若某字段语义要求规范化，必须在该字段 schema 中明确声明并版本化。
7. **可选字段**：区分“字段缺失”“显式 null”“默认值”。只有 schema 明确规定缺失等价于某默认值时，才可在规范化时展开默认值；不得普遍把缺失与 null 合并。
8. **封装**：将接口版本、操作、schema 身份/版本、规范化配置版本和规范化载荷共同纳入待摘要字节流，并采用无歧义的长度前缀或等价结构编码，防止字段拼接歧义。
9. **摘要**：对规范化字节流计算摘要，并同时存储算法标识、摘要值和规范化配置标识。SHA-256 可作为候选基线，但算法选择及协议版本兼容仍待 01-04 决策。

上述顺序是逻辑要求，不规定具体库或线上字节格式。任何实现必须通过跨语言黄金向量证明同一输入产生相同规范化字节和摘要。

## 4. 等价性与冲突规则

| 输入差异 | 期望判断 | 原因/条件 |
|---|---|---|
| 对象字段顺序不同 | 相同 | 对象字段排序由规范化配置固定 |
| 数组元素顺序不同 | 不同 | 默认数组有序；无序集合须由 schema 显式定义 |
| 整数文本 `1` 与 `01` | 不允许同时作为同一规范输入 | 严格解析；非规范表示拒绝，不能靠猜测折叠 |
| 十进制 `1.0` 与 `1.00` | 默认不自行判断 | 由 schema 的数值语义和编码规则决定 |
| 单位不同但物理量相等 | 不同，除非 schema 规定先转换至唯一基准单位 | 避免隐式单位推断 |
| 字段缺失与显式 null | 默认不同 | 只有 schema 明确等价时才可折叠 |
| 未知字段 | 拒绝，或由明确扩展字段规则处理 | 防止新旧版本对字段语义理解不一致 |
| 字符串 Unicode 规范形式不同 | 默认不同 | 不做隐式文本归一化 |
| 仅 correlation_id、message_id 或发送时间不同 | 相同 | 这些是关联/传输元数据，不是操作载荷 |
| interface/schema/canonicalization 版本不同 | 不可直接比较 | 必须经显式兼容规则或重新映射到同一规范版本 |

“物理意义相同”不能由通用摘要层推断。只有 schema 负责的、可测试的等价规则才允许规范化为相同指纹。

## 5. 请求账本和重试规则

设备端对 `device_id + session_id + request_id` 建立唯一记录，至少保存：

- interface_version、payload_schema_id/version、canonicalization_profile；
- digest_algorithm_id、payload_digest；
- operation、task_id、请求阶段、终态结果；
- 是否越过副作用边界、可恢复性/重启代际信息；
- 记录创建/更新的单调序号或等价审计信息。

处理规则：

1. 新身份：严格校验后创建记录，再按后续已定义的持久化/执行策略处理；“创建记录”不自动代表请求 Accepted。
2. 已存在身份且规范化版本、算法和摘要一致：返回该请求已记录的阶段/原结果；不得创建第二次副作用。
3. 已存在身份但摘要、操作类型或 schema 语义不一致：拒绝并报告 `REQUEST_ID_PAYLOAD_CONFLICT`；原记录不可覆盖。
4. 版本不同：不得把“摘要不同”直接判为恶意冲突，也不得把“摘要相同”直接判为语义等价；必须走显式兼容映射。无法可靠映射则返回 `UNSUPPORTED_SCHEMA_VERSION` / `CANONICALIZATION_VERSION_MISMATCH`，保持原请求状态不变。
5. 重试必须沿用原 session_id、request_id 和原始业务载荷语义。重新连接后应通过只读查询旧请求身份恢复结果，不得把原请求改写为新 session 的新请求。
6. 新的用户业务意图必须使用新 request_id；即使参数与旧请求完全相同，也不能复用旧结果冒充新动作。
7. 对可能产生物理副作用的请求，摘要匹配只证明“内容一致”，不证明“可以安全重放”。是否允许重试仍取决于设备账本阶段、掉电一致性证据和 TASK/SAFETY 守卫。

## 6. 版本兼容策略

- `canonicalization_profile` 是显式版本化协议资产，不可随实现升级而静默改变。
- 同一 profile 的不同实现必须通过相同黄金向量；测试应比较规范化字节，不只比较摘要结果。
- 新 profile 与旧 profile 并存期间，接收方可选择：支持旧 profile 并按旧规则验证；通过经测试的兼容转换映射到共同语义；或明确拒绝。不得静默降级。
- profile 迁移不得改变既有账本记录的身份或重算后覆盖原摘要。必要时保存原始 profile/digest，并追加派生映射记录。
- 设备升级、恢复出厂、配置迁移和账本恢复必须声明支持哪些历史 profile；缺少历史规则/记录时，历史请求结果保持 Unknown。
- 摘要算法升级必须携带算法标识；不同算法摘要不可直接逐字节比较。迁移应保留原摘要并以明确规则验证，不得只因算法不同就认定请求冲突。

## 7. 安全与实现边界

- 摘要用于完整性比较和去重，不提供身份认证、授权、抗重放会话保护或消息机密性；这些需要独立安全机制。
- 摘要算法应使用现代抗碰撞密码学哈希；SHA-256 是候选，不在本节点冻结。
- 设备端仍须校验当前会话、任务状态、操作权限、软限位、温度/故障状态和安全联锁。
- 对摘要碰撞、账本损坏、schema 解析差异或规范化实现不一致，采用失败关闭：拒绝或保持 Unknown/受限同步，不执行危险动作。
- 不得宣称 exactly-once。目标仍是防止无意重复副作用；无法证明时显式 Unknown 并安全受限。

## 8. 必需测试与验收证据

至少建立以下自动化测试类别：

- 跨语言/跨实现黄金向量：规范化字节和摘要一致。
- 字段排列、数组顺序、缺失/null、未知字段、重复键和 Unicode 差异。
- 整数边界、定点比例、负零、NaN/Infinity、溢出及单位/坐标语义。
- 相同请求身份相同载荷的重复提交只返回原阶段/结果。
- 相同请求身份不同载荷、不同 schema 版本、不同 profile/算法的冲突与兼容路径。
- 请求账本持久化/损坏/升级迁移及动作边界故障注入。

通过条件：规范化规则无隐式平台依赖；同版本实现有可重复黄金向量；版本不兼容明确拒绝或按经验证映射处理；请求冲突不会覆盖账本或触发副作用。当前这些均为待实现的测试要求。

## 10. 实验性黄金向量配置（不构成协议冻结）

为先验证规范化思路，仓库增加一个**仅供测试的原型 profile**：`json-int-prototype-0.1`。其规则为：

- 输入封装固定包含 `canonicalization_profile`、`interface_version`、`operation`、`payload`、`payload_schema_id`、`payload_schema_version` 六个字段；原型测试中拒绝额外或缺失的顶层字段。
- 使用 UTF-8 JSON；对象键按 Unicode 码点顺序排序；无多余空白；非 ASCII 字符直接 UTF-8 编码；数组保持原顺序。
- 仅允许字符串、整数、布尔值、null、数组和对象；本原型拒绝所有浮点数、NaN/Infinity、重复对象键和非法 Unicode。
- 对上述规范化字节计算 SHA-256；测试同时比较规范化字节和摘要。
- 该 profile 的整数/单位语义仅为测试夹具示例，不能据此推断打印机运动速度或其他物理参数。
