- **边界声明**：本文只分配逻辑责任与定义验收问题，不指定进程部署、存储产品、传输协议或数值参数；不证明固件掉电安全或真实设备安全。

## 1. 目的

将请求账本、设备侧去重、事件发布、重连同步和虚拟设备测试责任分配到明确组件，避免 HOST、COMM、TASK 和 SIM 对“谁记录、谁裁决、谁恢复”作出不同解释。

核心原则：

1. **HOST/COMM 的账本是主机侧审计与恢复记录，不是设备执行事实的权威来源。**
2. **TASK 是设备侧任务状态与副作用命令的最终裁决者；设备侧请求记录用于防止同一请求被重复执行。**
3. **事件发布方负责产生带有原始身份和顺序信息的事实；COMM 负责传输层接收、关联、去重和缺口检测；HOST/SYNC 负责将权威快照与事件流合并。**
4. **SIM/VDEV 只提供可控、可重复的虚拟行为，不得替代固件逻辑，也不得把模型结果描述为硬件事实。**
5. **证据不足时保留 Unknown / Synchronizing，不以“方便 UI”或“连接已恢复”为理由推断成功或失败。**

## 2. 组件责任矩阵

| 组件 | 必须负责 | 明确不负责 | 权威性 |
|---|---|---|---|
| HOST 请求协调器 | 创建业务请求；分配 request_id；保存原始请求摘要、session/task 关联、发送与确认事实；维护主机侧 request ledger；管理 Unknown；发起只读结果查询 | 不裁定设备动作是否实际执行；不把本地写入成功当作设备接受；不自动重放非幂等动作 | 主机侧审计记录权威；设备执行结果非权威 |
| COMM 通信适配层 | 传输收发；绑定 session_id；响应关联；消息级重复检测；事件流 sequence 缺口/乱序检测；超时和断连报告；保留原始消息标识 | 不决定任务是否合法；不把传输成功升级为 Accepted/Completed；不擅自生成设备终态 | 传输观察事实权威；业务执行事实非权威 |
| TASK 任务控制器 | 校验设备侧状态守卫；裁决 Start/Pause/Resume/Cancel 等任务状态转换；对副作用请求执行设备端重复请求保护；记录或查询设备已知请求阶段；关联 task_id 与执行结果 | 不负责主机 UI 状态；不把未确认动作标记完成；不允许旧 session 请求改变当前设备状态 | 设备任务状态及执行裁决权威 |
| MOTION / THERMAL / SAFETY | 执行前再次校验各自子系统约束；报告动作开始/完成/失败及故障；SAFETY 约束危险动作并管理故障锁存 | 不自行改变 HOST 请求账本；不绕过 TASK 的任务生命周期和 SAFETY 守卫 | 子系统观测/故障事实权威；跨子系统任务状态由 TASK 汇总 |
| 设备事件发布器（TASK/子系统内逻辑职责） | 为状态变化/执行结果分配 event_id、stream identity、sequence；附带 session/task/request/correlation 关联；保证发布的事件描述实际发生的状态或观测 | 不负责网络重传策略；不允许接收方根据墙钟时间猜测事件顺序 | 事件来源事实权威；交付成功由接收端确认 |
| SYNC 同步协调器（HOST 内逻辑职责） | 建立新会话同步流程；请求能力/任务/故障快照；记录每流 watermark；协调快照与增量事件；逐项查询旧会话未决请求；决定是否满足 Connected 准入条件 | 不裁定设备侧动作历史；不把未知请求改写为未执行；不在同步未完成时放行危险控制请求 | 主机同步完成状态权威；输入事实仍来自设备端 |
| LOG / 诊断存储 | 保存请求、响应、事件、快照、诊断、版本和时间线；支持按各类 ID 追踪 | 不作为任务状态裁决者；日志缺失不等于动作未发生 | 审计证据来源；不替代设备状态权威 |
| SIM / VDEV | 提供可注入断连、重启、丢失账本、重复/乱序事件、快照竞态的确定性虚拟环境；记录虚拟副作用 | 不实现第二套独立 TASK 业务规则；不宣称模拟结果证明真实 MCU/NVM/电气安全 | 仅虚拟模型事实 |
| TEST / CI | 执行契约测试；核对状态、结果、诊断和副作用；绑定源码 commit、模型版本和场景输入 | 不把未执行/跳过/阻塞用例计为通过 | 自动化验证证据 |

## 3. 请求账本分层与权威关系

### 3.1 HOST/COMM 主机侧账本

主机账本至少保存以下逻辑信息：

- 原始身份：device_id、原始 session_id、request_id、task_id（如适用）、correlation_id。
- 请求完整性：规范化请求摘要及摘要算法/规范化版本标识；原始请求内容或可审计引用。
- 生命周期事实：Created、Sent、已观察到的 Received/Accepted/InProgress/终态响应、Unknown 及其原因。
- 传输事实：发送尝试、连接代际、响应关联、超时/断连、重复响应和迟到响应。
- 恢复事实：查询时间、查询所用新 session_id、被查询的原始 session_id + request_id、设备返回结果、快照 watermark。
- 证据来源：消息来源、设备确认标记、日志关联 ID、代码/协议版本。

主机账本不得只存一个可覆盖的“当前状态”字段；必须能还原状态变化和证据来源。主机记录丢失或损坏时，不能据此推断设备未执行。

### 3.2 TASK/设备侧请求记录

设备侧记录至少区分：

- 请求身份：device_id、session_id、request_id。
- 请求内容身份：规范化载荷摘要及规范化版本。
- 执行关联：task_id、correlation_id、动作类别。
- 阶段事实：已识别、已接受、执行中、终态结果或 Unknown/不可恢复。
- 副作用边界：是否已进入任何可能产生物理副作用的执行阶段。
- 记录代际：记录是否跨设备重启保留；若不能保留，重启后必须显式声明历史结果不可确定。

TASK 只能在请求身份与载荷摘要一致时返回原请求阶段/结果。相同身份不同摘要必须拒绝，不能覆盖原记录。

### 3.3 两侧账本不一致时的规则

| 情况 | 处理 |
|---|---|
| HOST 记录 Sent，TASK 查询为 Accepted/InProgress | 以设备查询结果更新主机视图，并保留原发送/断连时间线 |
| HOST 记录 Unknown，TASK 查询为 Completed/Failed/Rejected | 保留此前 Unknown 的历史事实，追加设备权威查询结果；不得删除未知期间的审计记录 |
| HOST 有请求记录，TASK 明确未识别且能证明未接受 | 不自动重放；由上层决定是否创建新的业务意图和 request_id |
| TASK 记录存在，HOST 记录丢失 | 通过设备快照/查询恢复可确认的请求与任务事实；无法关联的记录归档并诊断，不猜测其 UI 意图 |
| TASK 重启后账本缺失，HOST 有未决请求 | 结果保持 Unknown；不得将“查无记录”解释为未执行 |
| 两侧返回相互矛盾的终态或载荷摘要 | 报告 PROTOCOL_ERROR / SYNC_INCONSISTENT；保持受限同步状态，保留双方原始证据 |

## 4. 请求处理责任时序

| 阶段 | HOST | COMM | TASK | 可对外报告 |
|---|---|---|---|---|
| 创建 | 分配 request_id，写入 Created | 无 | 无 | 本地已创建 |
| 发送 | 请求发送并记录发送意图 | 记录实际传输提交/失败 | 无 | 最多报告 Sent |
| 接收 | 等待设备事实 | 关联响应/接收确认 | 校验消息身份并记录识别 | Received 仅在设备侧明确确认后报告 |
| 接受 | 更新主机账本 | 转发设备响应 | 执行状态/能力/安全守卫，记录接受或拒绝 | Accepted / Rejected |
| 执行 | 订阅/查询 | 传递进度事件 | 驱动子系统并维护任务状态 | InProgress |
| 终态 | 记录设备确认结果 | 关联终态响应/事件 | 仅在完成条件满足后产生 Completed/Failed 等事实 | Completed / Failed |
| 断连 | 将无终态证据请求标为 Unknown | 报告连接丢失、保留原始关联 | 不因主机断连而自动假定动作停止 | ConnectionLost + Unknown |
| 重连 | 发起同步与旧请求查询 | 建立新 session 并隔离旧会话消息 | 提供当前快照及可恢复的旧请求记录 | Synchronizing，满足准入后才 Connected |

## 5. 设备重启、持久化与去重边界

### 5.1 必须回答的工程问题

在选择存储方案之前，架构必须先明确下列语义问题：

1. 设备在请求 Received、Accepted、InProgress、动作开始后、动作完成但响应发送前分别掉电，重启后能证明什么？
2. 去重记录写入与动作副作用之间是否存在原子性边界？若不存在，如何把不确定窗口显式呈现为 Unknown？
3. 记录何时可以回收？其保留期必须覆盖允许的请求重试/迟到消息窗口；具体窗口待 01-04/05 根据协议与平台决定。
4. NVM 写入寿命、掉电一致性、写入原子性和损坏检测如何验证？不能仅凭“使用持久化存储”就认为可靠。
5. 设备固件升级、配置恢复、恢复出厂设置或存储格式迁移是否改变 request ledger 的可查询性？必须声明行为。
6. session_id 生成机制必须避免重启后误复用；若无法保证，应使用设备启动代际/会话代际组合或等效可验证机制，具体实现待选型。

### 5.2 不允许的简化

- 不允许先执行运动/加热副作用，再把“写账本成功”当作唯一防重证据，而不分析中间掉电窗口。
- 不允许仅在 RAM 保存去重记录，却在重启后把旧请求返回为“未识别，因此可重放”。
- 不允许仅依赖 request_id 随机性代替载荷冲突检测与设备端状态守卫。
- 不允许因为设备快照没有列出某个历史 request_id，就断言该请求没有执行。
- 不允许在没有持久性证据时宣称 exactly-once。项目当前采用的目标是“副作用不得因重试被无意重复；无法证明时保持 Unknown 并安全受限”，不是未经证明的 exactly-once 承诺。

### 5.3 实现策略候选（不在本节点冻结）

| 候选策略 | 优点 | 风险/代价 | 当前状态 |
|---|---|---|---|
| 仅 RAM 请求记录 | 简单、写入快 | 重启后历史不可查询，未决动作扩大 Unknown 范围 | 不足以单独支持跨重启安全重试 |
| NVM 持久化请求记录 | 可恢复部分历史请求结果 | 需验证原子性、寿命、磨损、损坏恢复及动作/记录一致性 | 候选，待 01-04/05 评估 |
| 主机持久化 + 设备易失记录 | 主机审计完整 | 主机无法证明设备端副作用是否发生；不能安全重放未决动作 | 不能替代设备侧防重 |
| 事务日志/检查点与安全状态恢复组合 | 可更明确描述重启恢复边界 | 设计与验证复杂，仍需定义物理动作的不可逆窗口 | 候选，待平台和固件设计评估 |

不预设任何候选方案必然能实现原子 exactly-once。对运动、挤出、加热等物理副作用，恢复策略必须以可证明的设备状态和安全策略为依据。

## 6. 事件流与快照同步责任

| 责任 | 事件发布方 | COMM | SYNC/HOST |
|---|---|---|---|
| event_id 生成 | 必须 | 原样传递 | 验证重复/冲突 |
| stream identity / sequence | 必须在事件产生时赋值 | 保留顺序元数据并检测可见缺口 | 维护每流应用水位 |
| 重复投递 | 允许传输层发生 | 可识别消息重复但不擅自更改事件事实 | 确保同一事件只应用一次 |
| 缺口/乱序 | 不静默重编号 | 缓冲或上报缺口事实 | 决定等待补齐、请求重放或重新取快照 |
| 快照 watermark | 快照提供方必须给出一致水位 | 传递原样 | 校验快照与增量事件切面 |
| 旧会话/旧任务 | 保留原始身份 | 隔离旧会话消息 | 归档，不覆盖当前状态 |
| 无法恢复 | 明确返回不可查询/Unknown | 保留错误与关联 | 保持 Synchronizing/受限状态并要求处置 |

快照提供方必须说明：快照状态与 watermark 是否来自同一一致性切面。若无法保证原子快照，必须提供等价的版本/重试机制；否则接收端不能把同步标记为完成。

## 8. 对 01-03 验收的影响

本矩阵补足了现有语义提案中的组件责任分配，但仍有下列工作未完成：

- 在架构图和 ICD 中确认 SYNC 是 HOST 内部逻辑职责还是独立服务；本提案暂按 HOST 内部逻辑职责处理。
- 定义请求摘要的规范化规则、算法标识和版本兼容行为。
- 定义设备侧请求记录与物理动作之间的持久化/掉电一致性方案。
- 定义快照一致性切面与 watermark 的可实现协议。
- 把 TASK/HOST 账本矛盾、主机记录丢失、动作开始后掉电等场景补入测试规格。
- 由 01-04 决定传输、存储、进程部署和接口 schema；由 05 定义固件落地与安全恢复；由 07 实现故障注入与虚拟模型能力。

因此，本文件是责任矩阵和设计审查输入，不代表接口冻结、去重账本实现、掉电恢复验证或 SIL 测试通过。
